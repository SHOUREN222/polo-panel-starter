# 代理独立分站（多租户）设计方案

> 状态：设计稿（未开工）。先定方案与决策，再分阶段实现。

## 一、已确定的决策

| 决策点 | 选择 |
|---|---|
| 域名 | **子域名**（如 `daili1.example.com`） |
| 收款 | **B：每个代理接自己的支付网关**（客户的钱直接进代理），站长按批发另行结算 |
| 客户体系 | **各分站独立**（邮箱按站唯一，数据隔离） |
| 后台 | **两级**：站长（平台）+ 代理（分站，管不到平台底层） |

## 二、架构总览

- 采用 **`stancl/tenancy`**（Laravel 成熟多租户包），不手搓。
- **每个分站一个独立数据库**（package 默认的强隔离模式）——天然满足"客户独立、邮箱按站唯一"，从根上杜绝跨租户泄露。
- **中央库（central）**：只放平台级 + 共享数据（见下）。
- **租户解析**：按子域名解析当前分站，设定租户上下文；主站（`app.example.com`）= central 上下文，行为完全不变。
- **共享基础设施**（节点、onip 开通）仍属站长、所有分站共用，只按租户归属计量。

## 三、数据怎么切

**中央库（平台 + 共享）**
- `tenants`（分站：子域、状态、品牌、代理管理员、批发折扣/进货余额）
- 共享目录：`plans`（套餐目录）、`servers`/`nodes`、onip 配置、`payments`（平台自己的网关，仅主站用）
- 站长账号、平台设置

**每个租户库（分站私有）**
- `users`（该分站客户，邮箱按站唯一）
- `orders` / `subscription_instances` / `traffic_logs`
- `gift_cards` / `coupons` / `tickets` / `notices`
- 分站 `settings`（品牌/文案/客服）、分站 `payments`（**代理自己的网关凭证**）

> 迁移分两套：central 迁移 + tenant 迁移（每个租户库各跑一遍）。

## 四、四个决策的落地机制

### 4.1 子域名 + TLS
- 每分站一个子域，`tenants.subdomain` 唯一。
- TLS 用 **Caddy 按需签发（on-demand TLS）**：新分站子域一上线自动出证书，无需手工配。
- 中间件按 `Host` 解析租户 → 切库 → 渲染该分站。

### 4.2 收款按 B + 批发结算（关键）
采用 **B1「预付批发余额」** 机制，站长永不碰客户的钱、零资金池风险：

1. **代理收零售**：客户在分站下单，用**代理自己的支付网关**付款（钱直接进代理）。
2. **平台收批发（预付制）**：代理先给站长充值一笔**中央进货余额**（`tenants.wholesale_balance`）。
3. 分站每笔成交在**交付/开通时**，从该代理的中央进货余额**扣一笔批发成本**（= 套餐批发价，ISP 含 onip 真实开通成本）。余额不足则暂停交付、提示代理续充。
4. 差价（零售 − 批发）自然留在代理那边（他的网关已收到零售款）。

> 这其实是把现有"代理余额发卡"的思路升级到租户级：代理网关收零售、平台预付余额扣批发。复用现成的余额台账逻辑。

### 4.3 分站客户独立
- 每租户独立库 → **邮箱天然按站唯一**（`a@x.com` 在 A 站和 B 站是两个人）。
- 注册/登录/找回都在租户上下文内，互不可见。
- 订阅 token、订阅链接均在租户库内，互不冲突。

### 4.4 两级后台
- **站长（平台后台，central）**：管分站（开/停/批发折扣/进货余额）、共享节点、onip、套餐目录、平台设置。**唯一能碰底层的人。**
- **代理（分站后台，tenant）**：只管自己站——客户、订单、品牌/文案、自己的支付网关、工单。**碰不到**节点/onip/其它分站/平台设置，**也碰不到定价**（套餐与优惠券都是平台的，见 5.1 #1）。
- 复用现有"角色路由白名单"模式，但作用域收敛到租户内。

### 4.5 共享基础设施按租户归属
- **节点 / onip 开通仍是 central 的**：分站客户开通订阅时，调 central 的开通服务，产物（VLESS/中转/onip 线路）打上租户归属。
- **节点回报（UniProxy/流量上报）**：token 需带租户维度（或 central 反查映射），把用量记回对应租户库。这是多租户里最需要小心接的一处。

## 五、还需你拍板的开放问题

1. **零售定价权**：代理能**自定零售价**（推荐，是他的店），还是统一用平台价？
2. **套餐目录**：所有分站共用同一套餐目录、代理只选"上架哪些 + 定价"（推荐）？还是允许代理自建套餐？
3. **批发成本基准**：代理进货成本 = 「零售价 × 统一折扣」，还是你给**每套餐设批发价**（更可控，推荐后者）？
4. **代理网关**：EPay 支持多商户，代理各填自己的 `pid/key`；ISP 类订单批发含 onip 真实成本，需确保代理进货余额覆盖。是否只允许特定几种网关？
5. **分站开通流程**：站长在平台后台新建分站（填子域 + 指定代理管理员 + 批发折扣/初始余额），对吗？
6. **品牌**：分站可传 logo、站名、落地页文案、客服方式——范围到哪？

### 5.1 决策（已定，2026-07-16；#1#2#3 于 2026-07-17 修订，见下）
1. 零售定价权 → ~~代理自定零售价~~ → **⚠️ 2026-07-17 推翻：平台统一定价，代理不能改价。**
   代理的利润 = 批发折扣的差价，不给任何改价工具。实现上：`admin.plans` 与 **`admin.coupons`** 都不在 `User::TENANT_ADMIN_ROUTES` 里。
   **优惠券必须一起禁**——券会压低 `order->total_amount`，而批发正是按 `total_amount` 结算，一张 100% 券就等于白送平台节点服务且站长零收入（上线前实测复现过）。
2. 套餐目录 → **共用同一目录**，~~代理选上架 + 定价~~ → **代理既不能定价也不能选上架**（不允许自建套餐）。上架与定价都是平台的。
3. 批发成本基准 → ~~站长给每套餐设批发价~~ → **实际实现为「按分站统一折扣」**：
   `WholesaleService::wholesaleCost = round(order.total_amount × (100 − tenant.agent_discount) / 100)`，折扣在开分站时设定（0–90）。
   per-套餐批发价没有实现；若日后要做，注意换套餐订单的 `discount_amount` 里混着老套餐折抵，不能直接按原价收批发（会把代理多扣一次）。
4. 代理网关 → 各填自己的 EPay `pid/key`（网关种类先跟随主站支持的，后续再收窄）。
5. 分站开通 → 站长后台新建：子域 + 指定代理管理员 + 批发折扣/初始进货余额。
6. 品牌 → logo / 站名 / 落地页文案 / 客服方式。

### 5.2 技术选型补充
- **数据库仍用 SQLite**：现有库直接作为 **central（主站 + 共享）**，**不迁移现有数据**；每个租户一个独立 SQLite 文件（`stancl/tenancy` 的 SQLite database manager）。规模变大再评估迁 MySQL。
- **开发方式**：P1 起在**独立分支**开发，主站不中途上线；每阶段以"主站行为不变 + 全量回归绿"为准入。

## 六、分阶段实施（每阶段可验收、主站全程不停）

- **P0 设计定稿**：本文档 + 上面开放问题拍板。
- **P1 租户地基**：引入 `stancl/tenancy`，central/tenant 库拆分，子域解析中间件，主站跑在 central 上**行为不变**（回归测试全绿）。
- **P2 分站骨架**：开分站（tenants CRUD）、子域 TLS、分站独立注册/登录/仪表盘（空品牌）。
- **P3 交付打通**：分站客户能买套餐 → 调 central 开通服务 → 节点/onip 按租户归属交付 + 流量回报归位。
- **P4 收款 B + 批发结算**：分站接代理自有网关收零售；开通时扣代理中央进货余额（批发）；余额不足暂停交付。
- **P5 两级后台**：代理分站后台（客户/订单/品牌/网关/工单——**无定价、无优惠券**）；站长平台后台（分站管理 + 进货余额 + 共享底层）。
- **P6 品牌 & 打磨**：per-分站 logo/站名/文案、客服、订阅模板；端到端验收。

## 七、风险与缓解

| 风险 | 缓解 |
|---|---|
| 跨租户数据泄露（最高危） | DB-per-tenant 强隔离 + 每阶段隔离测试 + code review |
| 在活站上改地基弄坏主站 | 主站永远跑 central 上下文；P1 以回归测试全绿为准入；分阶段、可回滚 |
| 节点流量回报串租户 | token 带租户维度 + central 反查，专门测试覆盖 |
| 代理 onip 成本透支 | 进货余额不足即暂停 ISP 交付；开通前预扣 |
| 证书/子域运维 | Caddy 按需 TLS，自动化 |

## 八、工作量与节奏

- 这是项目里**最大的单项**，按 P1→P6 分阶段推进，每阶段独立交付、可停可验收。
- 不是一次成型；P1（租户地基 + 主站不变）是最关键也最该稳的一步,先做扎实再往上叠。
- 全程主站与现有付费客户不受影响。
